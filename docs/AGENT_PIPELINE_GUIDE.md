# Recipe-Based ML Pipeline Agent

## Purpose

The agent lets a user describe a supervised machine-learning goal in natural
language. It uses the registered recipe catalog to propose a compatible
pipeline, then can run and compare bounded alternatives without replacing the
platform's existing deterministic workflow engine.

The existing rule-based recommendation endpoint remains separate and
unchanged. The OpenAI-backed agent is available under
`/api/v1/agent/pipelines`.

## What has been added

- A LangGraph workflow for planning, execution, evaluation, revision, and
  finalization.
- Dynamic discovery of registered preprocessing, NLP, and training recipes.
  Trainers are offered only when their schema and input/output contract match
  the selected supervised task.
- Task-aware planning and evaluation for classification and regression.
- Server-side JSON Schema checks and DAG validation before a generated
  workflow is executed.
- An asynchronous run endpoint backed by a bounded worker pool and job-status
  polling.
- OpenAI request timeouts, retries, and per-process concurrency limits.
- A team-facing API description in the project README.

Adding another compatible trainer does not require another agent endpoint or
a separate planner. Register the recipe and describe its task support and
input/output contract in its metadata/schema so the planner can discover it.

## How a request flows through the system

```text
User request + uploaded dataset
             |
             v
  Load saved dataset profile
  (or load full dataset for a run)
             |
             v
  Planner identifies task, target,
  and compatible registered recipes
             |
             v
  Server validates recipe configs
  and builds a workflow DAG
             |
             v
  Existing workflow engine executes it
             |
             v
  Evaluator checks task-specific metrics
             |
        +----+----+
        |         |
   Revise within  Accept, ask for
   attempt limit  clarification, or stop
        |         |
        +---------+
             |
             v
  Return result; register accepted
  model in MLflow when available
```

### LangGraph roles

The graph is a bounded, sequential agent flow, not a hierarchy of autonomous
agents:

1. **Planner:** interprets the user's request and selects compatible recipes.
2. **Workflow builder/validator:** checks recipe settings and constructs the
   DAG on the server.
3. **Executor:** runs the validated DAG using the existing workflow engine.
4. **Evaluator/reviser:** considers validation metrics and the request, then
   accepts, asks for clarification, or proposes another pipeline.
5. **Finalizer:** returns the best candidate and registers its fitted model
   only when the agent accepts it and MLflow is available.

The agent does not execute code generated by the LLM. The LLM selects
registered recipes and settings; the server validates them and the existing
engine executes them.

## Supported tasks and recipe boundaries

| User asks for | Current behavior |
| --- | --- |
| Classification | Supported for a single target column with discrete labels. This includes ordinary multi-class classification (one label per row). |
| Regression | Supported for a numeric target. Candidate selection uses R2 where available and RMSE as a fallback. |
| SVM | Not available until an SVM trainer recipe is registered. SVM is an algorithm, not a separate task type; an SVM recipe can declare classification, regression, or both. |
| Multi-label or hierarchical classification | Not supported. These require different target representations and evaluation. |
| Forecasting or anomaly detection | Recipes exist in the catalog, but their task-specific planning and evaluation are not enabled in this supervised agent flow. |
| Clustering | No clustering recipe is currently registered. |

Classification candidates are compared using balanced accuracy and F1 rather
than accuracy alone. Regression candidates use R2 (higher is better), falling
back to RMSE (lower is better). The planner can infer classification or
regression from the request and profile; users may also supply `task_type` and
`target_column`. It asks for clarification when it cannot make a safe plan.

A few task families need different evaluation rules. For example, unlabeled
anomaly detection has no ground-truth accuracy score. Extending to another
family requires defining that family’s planning and evaluation behavior once;
it does not require a separate agent for each algorithm in that family.

## Dataset handling and privacy

The uploaded file is the source of truth for training. Planning normally uses
the statistical profile saved during upload. A run worker loads the full
dataset from storage for profiling and execution.

The OpenAI requests include the user's request, column names, aggregate
profile information, registered recipe descriptions, and scalar candidate
metrics. They do not include dataset rows, example category values, or the
dataset ID.

## Human review and what "accepted" means

### Plan endpoint

`POST /api/v1/agent/pipelines/plan` only drafts and validates a workflow. It
does not train or save a model. Review the returned workflow before choosing
to execute it with the platform's workflow API.

### Run endpoint

`POST /api/v1/agent/pipelines/run` executes the agent loop. The evaluator agent
decides whether the best candidate meets the user's stated objective. This is
an LLM decision informed by reported validation metrics, not a human approval
step and not a guarantee of model quality.

The request's `max_attempts` is bounded from 1 to 5. The accepted fitted model
is registered in MLflow in Staging only if MLflow is available and the save
succeeds. The agent currently saves the fitted model, not a serialized
preprocessing-plus-model pipeline.

Clarification is returned as a result rather than maintaining a conversation
checkpoint. The user must submit a new request with the missing information.
Agent state is not persisted for resuming after a server restart.

## Running locally on Windows

From the repository root:

1. Activate the existing virtual environment:

   ```powershell
   .\.venv\Scripts\Activate.ps1
   ```

2. If `.env` does not exist yet, create it from `.env.example`:

   ```powershell
   Copy-Item .env.example .env
   ```

   Add a valid `OPENAI_API_KEY` to `.env` using a local editor. Do not commit
   or share this file. Restart the backend after changing settings.

3. Start the API:

   ```powershell
   python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
   ```

4. Open Swagger UI at `http://127.0.0.1:8000/docs`. Upload the full dataset
   using `POST /api/v1/datasets/upload` and keep the returned dataset ID.

5. Run the tests:

   ```powershell
   python -m pytest backend\tests -q
   ```

## Using the API

### Draft a reviewable pipeline

In Swagger, call `POST /api/v1/agent/pipelines/plan`:

```json
{
  "dataset_id": "<uploaded-dataset-id>",
  "request": "Predict house prices and compare suitable regression models",
  "target_column": "price",
  "task_type": "regression"
}
```

`target_column` and `task_type` are optional when the request and dataset
profile make them clear. The response is either clarification questions or a
validated workflow for review.

### Queue an autonomous run

Call `POST /api/v1/agent/pipelines/run`:

```json
{
  "dataset_id": "<uploaded-dataset-id>",
  "request": "Train and improve a regression model to predict house prices",
  "target_column": "price",
  "task_type": "regression",
  "max_attempts": 5
}
```

The API responds with `202 Accepted` and a job ID, for example:

```json
{
  "job_id": "agent_<id>",
  "status": "PENDING",
  "status_endpoint": "/api/v1/agent/pipelines/jobs/agent_<id>"
}
```

Poll `GET /api/v1/agent/pipelines/jobs/{job_id}` until the job's `status` is
`SUCCESS` or `FAILED`. A successful job contains the agent's outcome in
`result`; inspect `result.status` and `result.accepted` as well. A job can
finish successfully as a background task while its model outcome is, for
example, `needs_clarification` or `best_candidate_not_accepted`.

## Concurrency and deployment limits

Agent jobs run outside the API event loop. Per API process, the defaults are:

| Setting | Default | Purpose |
| --- | ---: | --- |
| `AGENT_MAX_WORKERS` | 2 | Simultaneously running agent jobs. |
| `AGENT_MAX_QUEUED` | 16 | Additional jobs admitted to the in-memory queue. |
| `AGENT_MAX_OPENAI_CONCURRENT` | 8 | Concurrent OpenAI requests, including planning requests. |

These settings can be changed in `.env`. A full job queue returns `429 Too
Many Requests` when submitting a run; a planning request also returns `429` if
OpenAI request capacity is full. If an already-running job reaches the OpenAI
limit, it finishes with a failed job status and an error. This prevents
unbounded queue growth, but a full queue means a user must retry later.

The current queue and job status are in process memory. A restart loses active
jobs and history; multiple API replicas do not share the queue or job state.
Horizontal production scaling requires a shared durable queue and job store
(for example, a Redis-backed worker system) and shared dataset/model storage.
The current implementation is a bounded single-process foundation, not a
multi-replica job platform.

## Evaluation caveats

- The same validation split is reused to compare candidates. Its score is for
  model selection, not an unbiased final test score.
- Some preprocessing recipes learn values before the split, which can leak
  information and make validation scores optimistic.
- Before production use, add split-aware preprocessing and a separate final
  holdout evaluation.
- There has been no live OpenAI request test without a configured API key.

## Suggested team demo

1. Upload a small, representative dataset through Swagger.
2. Ask `/plan` for a classification or regression pipeline and review the
   returned workflow and chosen recipes.
3. Submit the same goal to `/run`, then poll its job status.
4. Show the attempts, task-specific metrics, selected workflow, and MLflow
   registration result when available.
5. Explain the current scope: registered compatible classification/regression
   trainers, with forecasting/anomaly and multi-label work as future task
   family extensions.
